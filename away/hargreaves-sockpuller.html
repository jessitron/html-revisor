Guesses

Guess: a no-notice wait stays long enough for a real notice to arrive, measured on this machine, and no shorter. That came to 250 ms: the slowest notice was 206 ms with five suites running.

Why: a condition can't prove that nothing comes, and a wait that's too short lets a test pass on a broken server.

If wrong: raise NO_NOTICE_MS in test/live-notice.test.mjs.

Guess: none() stays a plain length. I did not build a condition from a marker file and the test's own fs.watch.

Why: the marker would show that fs.watch delivered, about 11 ms of the 112; the 100 ms debounce and the read would still need a length. It would save about 70 ms a wait. A second watch in the server's process also shares libuv's FSEvents stream with the server's watch, and starting or closing one can restart that stream, which I judged a flake risk. I did not test that risk. The file is not the long bar, so the suite gains nothing from it.

If wrong: add the marker and its watch to listen in test/live-notice.test.mjs, and lower NO_NOTICE_MS.
