html-revisor: observability

What html-revisor tells Honeycomb about a save, from your keystroke to the file on disk and back, and the queries that show it.

Turn it on

HRV_TELEMETRY=1 OTEL_EXPORTER_OTLP_ENDPOINT=https://api.honeycomb.io OTEL_EXPORTER_OTLP_HEADERS=x-honeycomb-team=<ingest key> ./run

HRV_TELEMETRY is the switch. Without it the server sends nothing, whatever OTEL_* variables it inherits. With it, the standard variables say where spans go. Spans land in team modernity, environment local, dataset html-revisor (the service name). .be in this repo holds the key and the variables.

The server tells the page that telemetry is on, and only then does the browser record spans. A failed export prints telemetry export failed on the server's stderr.

One save, as a trace

A directive typed and saved, closed with Escape while it went out. The browser's spans are purple; the server's are blue. Times from a real run.

The save span starts when the change goes out. The typing before it is in two attributes: hrv.wait.ms since the first keystroke, hrv.quiet.ms since the last. The round trip is about 12 ms on a small page.

Spans

Span Where From → to Attributes
save directive, save markdown browser from when we decide to save, until the page has been updated hrv.change.kind, hrv.scope.id, hrv.element (tag name), hrv.edits (keystrokes in this one save), hrv.wait.ms (first keystroke → sent, queue included), hrv.quiet.ms (last keystroke → sent), hrv.html.before, hrv.html.after (markdown saves), hrv.markdown.before, hrv.markdown.after or hrv.directive.before, hrv.directive.after; each text with a .length
PUT browser PUT sent → answer received; its traceparent makes the server span its child. client.js makes it; no instrumentation library. hrv.queued (changes behind it), http.response.status_code
apply browser answer received → page updated
close box (event) browser a dot on the save going out when the box closes (Done, Escape, a click away, another box); none when no save is going hrv.close.by, hrv.scope.id, hrv.pending (saves still waiting behind it)
PUT change server request → response; a child span per step hrv.page, hrv.page.bytes, hrv.change.kind, hrv.scope.id, hrv.change.bytes, hrv.directive.count, hrv.answer.bytes, hrv.conflict
GET page server request → response; a child span per step hrv.page, hrv.page.bytes, hrv.normalized, hrv.element.count, hrv.scope.count, hrv.answer.bytes

Browser spans carry hrv.side = browser. A conflict or a failed save marks the browser's spans as errors. A text attribute stops at 50,000 characters, under Honeycomb's 64 KB limit; its .length is the full count.

Queries

Each opens in Honeycomb over the last two hours of dataset html-revisor.

  • How long does a save take? Heatmap of save directive and save markdown.
  • Where does a save's time go? PUT and apply, by kind of save.
  • How long before a save goes out? hrv.wait.ms and hrv.quiet.ms, by kind of save.
  • Which server step costs the most? Total and P95 time of each step of GET and PUT.
  • Which closes land mid-save? close box events, by what closed the box and how many saves waited behind.
  • Do bigger pages save slower? GET and PUT time by page and page size.
  • What went wrong? Spans marked as errors (status_code 2): conflicts and failed saves.
  • The slowest saves, one row per trace. Click a trace ID to see its waterfall.

How the browser's spans get there

The browser has no OpenTelemetry SDK. client.js records each span as a plain object (trace ID, span ID, parent, start and end, attributes, events) and posts a batch to /.hrv/spans every 2 s and when the tab hides. The server makes each one an OTel span with the browser's IDs and times, and sends it with its own spans. That route makes no span of its own.

Two reasons for no SDK. client.js is a plain script inlined into every page, with no build, and the web SDK would need a bundle. And a browser exporting to Honeycomb would need the ingest key in the page; through the server, the key stays on the server.

Checking it

test/telemetry.test.mjs checks the spans against a stand-in collector. Given .be's variables, it also sends to Honeycomb (dataset html-revisor-test) and prints a run ID and trace ID. The ingest key can't read; an agent finds the trace with the honeycomb-modernity MCP.
