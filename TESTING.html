How we test

136 tests, all passing, in 57 seconds. One test file holds 56 of those seconds, and one page in it holds 36.

The suite

npm test is node --test. It runs each file under test/ in its own process, several at once, so the suite takes as long as its slowest file. No dependencies: deploy runs these tests inside iterate-on-docs, where npm install can't run.

Every ship runs the suite three times: once by hand, once in ./deploy, once in iterate-on-docs' release. That's three minutes of waiting, on the same commit. Deploy and release both test the copied files in iterate-on-docs/html-revisor/, so a file deploy missed fails there. Deploy tests the copy before it commits it; release tests it again. Release's run catches a hand edit to the copy, or a release with no deploy in front of it.

What the round-trip file checks

Two properties. Each runs over every scope of every page it's given: no examples, no picking.

Round-trip

Scope → markdown → scope gives back the same HTML, IDs and directives included. Opening a box and saving it unchanged leaves the file unchanged.

Reconcile

Edit a scope (change a word, insert, remove, swap, or word and insert), save its markdown over the old one. Each element keeps its ID and its directive.

Tidy markdown

Pages in the shapes agents write most come out as markdown, HTML only for section and card tags.

The same checks run two ways: as property tests on generated pages, and on specific files.

Where to cut

Floor: 1 KB. Each bug the mintlify page caught showed up in a scope that size or smaller. An element over the cap stops being a scope: no Content field, no round-trip test. It can still take a directive.

My lean: 2 KB, about 30 lines in the box. It takes every body and every whole section, and keeps most cases, cards, and tables.

Which length

HTML size and markdown size part ways around an SVG. OVERVIEW's #architecture-now is 4.7 KB of HTML and 123 characters of markdown: the diagram is one token in the box. A cap on markdown keeps it a scope; a cap on HTML cuts it.

Measuring markdown means rendering it, and rendering a giant wrapper is the cost we're cutting. Text length (textContent) is cheap and might track markdown well enough. To check before deciding.

Sampling 10% instead

Sampling 10% of mintlify's scopes would cut its 30.6 s of reconcile to about 3 s on average. But the 9 scopes of 64 KB and up hold 38% of the work, so the time swings with whether the sample picks one. And it keeps testing scopes we don't want to support. With a cap in place, the long bar shrinks anyway; sample after that if it's still long.

Recommendations

  1. First: limit the size of what counts as a scope. A product decision, and the tests follow it: nobody edits 288 KB of markdown in a textarea, so the tests stop checking it. Pick the cap from Scope sizes, 1 KB or more. Saves on deep pages get faster too. The yak's note asks to keep round-trip running on big elements anyway; drop that, since we don't support them. The yak waits on Telemetry today. Round-trip file ~16–27 s, by the cap.
  2. Then split roundtrip.test.mjs into files. Property tests on generated pages in one file, tests on specific files in another, with shared generators and checks in test/roundtrip-lib.mjs. Split further if one file still runs long. node --test runs files side by side, so the suite waits on the longest. Same tests, same coverage. Measure after the cap; the cap decides how much this buys.
  3. Run the suite once per ship. Deploy and release test the same commit back to back. Release could skip its run when the vendored commit hasn't changed since the deploy that tested it. That change lives in iterate-on-docs.

Not recommended: dropping or shrinking the mintlify page. It's the one page in the suite shaped like the wider web, and it caught three bugs in its first day.
