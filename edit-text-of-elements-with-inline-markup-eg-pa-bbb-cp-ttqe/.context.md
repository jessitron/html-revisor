Text editing covers only elements whose children are all text. Mixed content shows the comment box only, so markup isn't flattened. Could edit each text run, or use contenteditable.

Research 2026-10-11 (HTML Living Standard + editing specs):
- Spec boundary: "phrasing content" (text + inline elements: b, i, em, strong, code, a, span, kbd, sub, sup, mark, small, abbr, time, q, s, u, var, samp, br, img, wbr...). A run of phrasing content is a "paragraph" (HTML §3.2.5.4). Replace isTextElement ("no child elements") with "all descendants are phrasing content".
- Option A (recommended first): keep the textarea. Diff old textContent vs new text (common prefix/suffix), map the changed offset range onto text nodes, apply it there. Inline elements survive. Insertions at a boundary go to the left run, except into <a>/<code> ends (ProseMirror "inclusive marks" idea). Remove inline elements left empty. Atoms (img, br, wbr) become U+FFFC in the textarea and can't be edited. Idempotent on resend: diff against file is empty the 2nd time. Watch whitespace collapsing: client collapses/trims, file text has raw whitespace; map offsets through the collapse.
- Option B: contenteditable="plaintext-only" on the element in the page (cross-browser since Firefox 136, 2025). Existing markup stays, no new formatting, paste is plain. Browser may still insert <br>, &nbsp;, or merge/drop elements on cross-boundary delete. Server must parse the HTML fragment in context and reject anything not phrasing content.
- Use beforeinput (Input Events) to block insertParagraph / formatting / paste-as-HTML if we go with B.
- EditContext API is Chromium-only; skip.
