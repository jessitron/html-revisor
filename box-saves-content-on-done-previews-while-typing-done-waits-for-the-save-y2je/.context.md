Study 2026-10-13 (Jess: edits aren't instantaneous; Done must make sure edits land).

Measured:
- client.js already debounces 400 ms, sends one PUT at a time, coalesces queued edits, reads the base at send time, and closeBox() flushes. Headless-Chrome runs at 60 ms/key and 450 ms/key: every edit landed, Done included.
- PUT round trip: 4 ms on a small page, 8-30 ms on OVERVIEW/PLAN/try-me. The server is not the lag; the debounce is. Typing steadily, the page behind never updates until a 400 ms pause.
- Done closes the box first, then saves. If that save fails (412 because the file changed, server down), the text is gone with the box; the docket says 'copy what you wrote' with nothing left to copy. A failed PUT also stops the queue: changes behind it wait for another keystroke. No beforeunload guard: reload inside 400 ms drops the edit.
- Hazard: every pause commits a half-typed state. Typing over a link that holds a directive, 'see [the docs](https://x.org now' saved mid-edit turns the link to text, and the directive is dropped (carryDirectives: deleted element takes its directive). Fixing the text brings back the link with a new ID and no directive. Saving sooner makes this worse.

Proposal: Content previews while typing and writes once on Done.
- Server: a preview request (same body as PUT markdown, no write) answers the served HTML. ~10-30 ms, so no debounce needed: one in flight, latest text coalesced.
- Done / esc / cmd-enter / click-away: PUT the content once, against the base from when the box opened. Box shows 'saving…' and stays open until the answer; on failure it stays open with the text and the error.
- Directive field: open question for Jess, keep saving as she types (agents see it at once) or commit on close too (uniform; ends the 'wait 20 s for mtime' gotcha).
