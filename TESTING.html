How we test

136 tests, all passing, in 57 seconds. One test file holds 56 of those seconds, and one page in it holds 36.

The suite

npm test is node --test. It runs each file under test/ in its own process, several at once, so the suite takes as long as its slowest file. No dependencies: deploy runs these tests inside iterate-on-docs, where npm install can't run.

Every ship runs the suite three times: once by hand, once in ./deploy, once in iterate-on-docs' release. That's three minutes of waiting, on the same commit.

What the round-trip file checks

Two properties. Each runs over every scope of every page it's given: no examples, no picking.

Round-trip

Scope → markdown → scope gives back the same HTML, IDs and directives included. Opening a box and saving it unchanged leaves the file unchanged.

Reconcile

Edit a scope (change a word, insert, remove, swap, or word and insert), save its markdown over the old one. Each element keeps its ID and its directive.

Tidy markdown

Pages in the shapes agents write most come out as markdown, HTML only for section and card tags.

Why that page costs so much

Both properties do work in proportion to the size of each scope, and scopes nest. A paragraph is counted once on its own and once more inside every scope around it. Markdown takes about 0.9 µs per byte of scope, on every page.

A correction: the yak that fixed this page recorded the suite growing from 22 s to 36 s when it arrived. Those runs were failing, and a failing page test stops at its first bad scope. The commit that made the page pass takes 60 s today, same as main. The suite hasn't slowed since.

Recommendations

  1. Split roundtrip.test.mjs into files. Move the generators and checks into test/roundtrip-lib.mjs, and give each property-and-page pair its own small test file: mintlify round-trip, mintlify reconcile per edit, the repo's pages, generated pages. node --test runs them side by side. Same tests, same coverage. Wall time ~10 s, set by the slowest mintlify edit (6.6–8 s). An estimate; measure it after.
  2. Reconcile small scopes on the frozen pages; round-trip all of them. The round-trip test keeps every scope, the wrappers too. The five edit tests skip scopes over 50 KB. My guess: a big scope runs the same matching a small one does, on more elements. The page's bug history agrees; nothing in the code proves it. Saves ~26 s of CPU; with the split, the suite waits on the slowest generated-page test, about 3 s by estimate.
  3. Do the yak "Limit the size of what counts as a scope". A product decision, not a test one: nobody edits 288 KB of markdown in a textarea. When the wrappers stop being scopes, saves on deep pages get faster and so do these tests. The yak asks that the round-trip property keep running on big elements anyway; recommendation 2 is that part.
  4. Run the suite once per ship. Deploy and release test the same commit back to back. Release could skip its run when the vendored commit hasn't changed since the deploy that tested it. That change lives in iterate-on-docs.

Not recommended: dropping or shrinking the mintlify page. It's the one page in the suite shaped like the wider web, and it caught three bugs in its first day.
